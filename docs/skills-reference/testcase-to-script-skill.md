# 用例转脚本 Skill（通用版，归档参考）

> 来源：用户提供的实际项目提炼规则。精修模块（#3 用例管理 W5）参考用例层部分；转脚本模块（#4）参考脚本层部分。
> 边界：精修在转脚本之前做用例质量提升，只涉及用例文本规则；脚本代码层规则留给 #4。

---

## 一、输出边界

唯一目标：**Python + Playwright + pytest** 标准 UI 自动化测试。

禁止输出 JavaScript、TypeScript、Cypress、Selenium，除非用户明确要求。

---

## 二、入口模式

| 用户输入 | 模式 | 说明 |
|---------|------|------|
| 测试用例 + 步骤 + 预期结果 | 用例直转 | 最常用，把手工用例转成脚本 |
| 已有工程 + 新用例 | 增量模式 | 不从零开始，先缺口分析再写代码 |
| PRD / 需求文档 | PRD 生成 | 从需求推导测试场景再生成 |
| 已有脚本跑不通 | 调试修复 | 定位归因，修复脚本 |
| 已有脚本要优化 | 脚本增强 | 检查断言、定位器、数据管理 |

## 三、全局硬规则

### 3.1 定位策略优先级（从高到低）

1. `page.get_by_role("button", name="登录")` — 语义化角色
2. `page.get_by_text("确认提交")` — 文本
3. `page.get_by_label("用户名")` — 表单标签
4. `page.get_by_placeholder("请输入密码")` — 占位符
5. `page.locator("css=selector")` — CSS 选择器（最后手段）

### 3.2 禁止索引定位

禁止在 click/fill/select 中使用 `.first`、`.nth(i)`、`.last`。

例外：`expect(locator.first).to_be_visible()` 允许——locator 匹配多个元素时 expect 需要 `.first` 避免 strict mode error。

区分原则：click 用 `.first` 可能点错元素（禁止），expect 用 `.first` 只是检查第一个元素是否可见（允许）。

### 3.3 禁止永真断言

断言必须验证操作导致的业务结果，不能只验证固定按钮/菜单/页面未报错。

永真断言黑名单：

| 模式 | 为什么永真 | 正确做法 |
|------|-----------|---------|
| `expect(button).to_be_visible()` | 按钮始终可见 | 验证点击后的业务结果 |
| `assert len(results) > 0`（不筛选时） | 页面默认有数据 | 筛选后验证结果符合筛选条件 |
| `assert "字段名" in text` | 标签文本始终存在 | 提取字段值并断言值非空 |

断言自检方法（思想实验）：写完断言后——如果把操作步骤全部注释掉，断言还能通过吗？能通过 = 无效，必须改。

### 3.4 等待策略优先级

| 优先级 | 策略 | 示例 |
|--------|------|------|
| 1（首选） | expect 断言自带等待 | `expect(locator).to_be_visible(timeout=10000)` |
| 2 | API 响应等待 | `page.wait_for_response(lambda r: "/api/" in r.url)` |
| 3 | 元素状态等待 | `locator.wait_for(state="visible", timeout=10000)` |
| 4 | 页面加载状态 | `page.wait_for_load_state("networkidle")` |
| 5（最后手段） | 固定等待 | `page.wait_for_timeout(500)` — 仅用于动画 |

### 3.5 其他硬规则

- 禁止编造 DOM：没有 DOM Map、知识库或 MCP 探查结果时，不得声称 locator 已验证
- 测试数据集中管理：业务数据集中在 `config/test_data.py`，脚本只引用变量
- 封装一致性：可复用操作封装到 `common/<module>_base_test.py`，用例只组合业务步骤
- 用例一一追踪：每条用例标注 `@pytest.mark.case_id("...")`
- 未执行不得声称通过：没有运行 pytest 并看到结果，不得声明测试通过

## 四、用例直转流程

### Step 0：用例标准化

必填字段：

| 字段 | 必填 | 缺失处理 |
|------|------|---------|
| title | 是 | 用步骤摘要生成 |
| steps | 是 | 缺失则阻塞，不能生成 |
| expected_results | 是 | 缺失则阻塞，不能生成 |
| case_id | 否 | 自动生成，标注"待确认" |
| priority | 否 | 默认 P1 |

steps 或 expected_results 为空的用例，直接列入"不可生成清单"，不硬凑。

### Step 1：步骤 → Playwright 动作

自然语言步骤转结构化动作意图。映射表：

| 测试步骤 | 动作类型 | Playwright 意图 |
|---------|----------|-----------------|
| 打开/进入/访问 X 页面 | navigate | goto 或菜单导航 |
| 点击 X | click | 定位按钮/链接/菜单后 click |
| 输入 X 为 Y | fill | 定位字段后 fill |
| 选择 X 为 Y | select | 下拉框选择 |
| 勾选 X | check | checkbox check |
| 新增 | create | 点击新增，填写表单，保存 |
| 编辑 | edit | 定位目标行，点击编辑，修改并保存 |
| 删除 | delete | 定位目标行，点击删除，确认，验证消失 |
| 审批/提交/通过 | workflow_action | 执行业务按钮并验证状态流转 |

这一步只输出动作意图，不写选择器。禁止编造 CSS selector。

### Step 2：预期结果 → 断言

| 预期结果 | 断言类型 | 推荐做法 |
|---------|----------|---------|
| 提示 X | toast_message | 验证提示组件包含具体文案 |
| 列表出现 X | row_visible | 验证目标数据行可见 |
| 状态变为 X | status_changed | 验证状态字段为 X |
| 字段显示 X | field_value | 验证字段值等于或包含 X |
| 弹窗关闭 | dialog_closed | 仅作为中间断言，必须继续验证业务结果 |
| 系统正常处理 | ambiguous | 模糊预期，标注"待验证" |
| 以实际为准 | ambiguous | 等同"待验证" |

标注为"待验证"的断言，在调试阶段由人工实际操作确认页面真实反应后写入知识库，下次自动生效。

### Step 3：DOM 匹配

三级优先级：
1. 用户提供的 DOM Map（最可信）
2. 项目知识库（历史探查记录）
3. Playwright MCP 实时探查（兜底）

没有以上任何一个来源时，只能输出草稿脚本，禁止编造 DOM。

### Step 4：代码生成 + 步骤对照表

代码生成后必须输出对照表：

```
| 步骤 | 用例要求 | 代码实现 | 状态 |
|------|---------|---------|------|
| 1 | 点击新增按钮 | click_add_button() | ✅ |
| 2 | 输入名称 | fill_name("测试A") | ✅ |
| 3 | 验证列表出现新数据 | — | ❌ |
```

- ❌ 的步骤必须补齐代码后才能进入调试
- 验证类步骤必须有 assert，不能只写 `logger.info`

## 五、调试协议

### 5.1 三轮渐进式验证

| 轮次 | 做什么 | 禁止什么 |
|------|--------|---------|
| 第 1 轮 | 跑 3-5 个关键用例 | 禁止跑全量 |
| 第 2 轮 | 只跑失败用例 | 禁止跑全量 |
| 第 3 轮 | 全量验证 | 唯一允许跑全量的轮次 |

超过 3 轮 = 停止，标记"待人工确认"。

### 5.2 失败归因四分类

只有"脚本问题"才能改代码：

| 特征 | 归因 | 能改代码？ |
|------|------|-----------|
| 定位器找不到元素 / 超时 | 脚本问题 | ✅ |
| 多个用例同一函数失败 | 脚本问题（共性 bug） | ✅ |
| 断言值和预期不符（页面行为错） | 页面 Bug | ❌ 标 xfail |
| 含"重复""已存在""唯一" | 数据/环境问题 | ❌ 硬停 |
| 第一次通过第二次失败 | 数据/环境问题 | ❌ 硬停 |

### 5.3 调试纪律

- 简单问题（locator 拼写错误、strict mode、import 错误）：直接修复，事后补记录
- 复杂问题（多个用例同一函数失败、不确定归因）：必须先输出诊断卡再改代码

## 六、知识库回写

MCP 探查完必须写回项目知识库。

写回时机：
- 探查完成后 → 立刻写回（不等代码跑通）
- 调试通过后 → 补充调试中发现的 DOM 差异

写回内容：
- 页面 DOM 结构树（弹窗/表单/列表的层级关系）
- 关键元素选择器（按字段/区域分组）
- 交互方式（click/fill/select + 特殊处理）
- 可用选项列表（如下拉框有哪些选项）
- 踩坑记录（如"JS click 不触发 Vue 事件"）

效果：探查 → 记录 → 复用 → 不用再探查。第一次探查花十几次 MCP，第二次读知识库直接用。

## 七、质量自检（8 项）

| # | 检查项 | 要求 |
|---|--------|------|
| 1 | 测试数据集中管理 | 业务数据全部从 test_data.py 引用 |
| 2 | 断言有效性 | 无永真断言（思想实验：注释掉操作后断言还能过吗？） |
| 3 | 封装一致性 | 无绕过 base_test 的操作 |
| 4 | 未使用的导入 | 已清理 |
| 5 | 重复用例 | 无重复 |
| 6 | 硬编码等待 | wait_for_timeout 仅用于动画（≤500ms） |
| 7 | 数据隔离 | 编辑/删除用例有专属数据 + teardown |
| 8 | 场景完整性 | 每个功能点都有对应用例 |

全部 ✅ 才能输出最终结果。任何 ❌ 必须修复后重新输出自检表。

## 八、工程结构（参考）

```
your-project/
├── config/
│   ├── env.py              # 环境配置（URL、账号）
│   ├── elements.py         # 元素定位配置
│   └── test_data.py        # 测试数据集中管理
├── common/
│   ├── login_base_test.py  # 登录封装
│   ├── xxx_base_test.py    # 各模块封装
│   └── ...
├── testcases/
│   ├── test_xxx.py         # 各模块用例
│   └── ...
├── conftest.py             # session 登录 + 失败截图
├── pytest.ini              # markers + 执行参数
└── run.py                  # 一键执行入口
```

三层分离：config 管配置、common 管封装、testcases 管用例。用例只调用封装方法，不直接操作页面。

## 九、使用建议

1. 已有工程 + 新用例 → 用增量模式，不要走完整流程
2. 遇到 strict mode error → 加 `.first` 到 expect，这是 Playwright 的设计
3. 简单报错直接修，不用每个都填诊断卡
4. 新增操作也是消耗性的，用完要 teardown 清理
5. 先试跑 2-3 个用例再批量生成，避免基础设施问题导致大面积失败
6. MCP 探查前先读知识库，探查后立刻写回知识库
7. 代码写完后做步骤对照表，逐条确认每步有代码实现
8. 不同的项目、不同的人，踩的坑不一样——流程经验补充到规则里，项目经验写进知识库
